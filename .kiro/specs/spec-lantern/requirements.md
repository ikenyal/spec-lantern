# Requirements Document

## Introduction

spec-lantern is a tool that resurrects abandoned "vibe-coded" applications — TypeScript/React apps generated by AI tools such as Lovable, Bolt, or v0. These apps often ship with misleading code comments and undocumented behavior, so an agent that only reads source code draws wrong conclusions.

The guiding insight comes from a feasibility test: an agent that only READS code trusted a misleading comment ("Reverse to have most recent month first") and predicted a property would PASS, while executing a property-based test proved it FAILS (the oldest month was shown first). spec-lantern therefore never stops at reading — it EXECUTES extracted properties against the real code inside an isolated runner and compares the agent's prediction with the actual result.

The product has three deliverables that cooperate as one pipeline:
1. A Kiro Power (POWER.md plus steering) that guides Kiro through reverse-engineering a spec, separating intended from current behavior, extracting claims into properties, and generating fixes for confirmed bugs.
2. An MCP Server that executes those properties inside an isolated runner (rootless Podman locally; AWS later) and returns structured results.
3. A web Lantern Report UI that displays predicted versus actual outcomes per property, lists confirmed bugs with counterexamples, and is additionally available as a publicly accessible hosted demo.

This document defines the requirements for that pipeline. Design and implementation details are deferred to later phases.

## Glossary

- **spec-lantern**: The overall product comprising the Kiro Power, the MCP Server, and the Lantern Report UI.
- **Target_Repo**: A TypeScript/React application, supplied by the user, that spec-lantern analyzes.
- **Target_Repo_Copy**: A copy of the Target_Repo to which generated fixes are applied, so that the original Target_Repo is never modified.
- **Kiro_Power**: The Kiro Power artifact (POWER.md and steering files) that guides Kiro through reverse-engineering, property extraction, and fix generation.
- **MCP_Server**: The Model Context Protocol server that receives properties and executes them inside the Isolated_Runner.
- **Isolated_Runner**: The sandboxed execution environment where Target_Repo code runs. Locally a rootless Podman container; later an AWS-based runner.
- **Lantern_Report_UI**: The web interface that presents predicted versus actual property results and confirmed bugs.
- **Hosted_Demo**: A publicly accessible deployment of the Lantern_Report_UI on AWS that presents sample Lantern_Reports without requiring any local installation.
- **Reverse_Engineer**: The pipeline step that produces a Kiro spec (EARS requirements and a design with Correctness Properties) from a Target_Repo.
- **Correctness_Property**: An executable assertion about Target_Repo behavior derived from a claim, expressed as a property-based or example-based test.
- **Component_Rendered_Property**: A Correctness_Property derived from the output produced by rendering a React component in a jsdom environment, used when the asserted logic is embedded in a component rather than exported as a standalone function.
- **Claim**: A statement of intended behavior found in a code comment, a requirement, or other documentation within the Target_Repo.
- **Observed_Deviation**: A documented difference between intended behavior (as claimed) and current behavior (as executed).
- **Predicted_Result**: The PASS or FAIL outcome that Kiro predicts for a Correctness_Property by reading code, recorded before execution and immutable once execution begins.
- **Actual_Result**: The PASS or FAIL outcome produced by executing a Correctness_Property inside the Isolated_Runner.
- **Pre_Fix_Result**: The Actual_Result of a Correctness_Property recorded before any fix is applied for a Confirmed_Bug.
- **Post_Fix_Result**: The Actual_Result of a Correctness_Property recorded after a fix has been applied to the Target_Repo_Copy and the property has been re-executed.
- **Property_Transition**: The pairing of a Correctness_Property's Pre_Fix_Result and Post_Fix_Result (for example, FAIL to PASS, FAIL to FAIL, or PASS to FAIL).
- **Fix_Task**: A generated unit of work describing a code change intended to resolve a Confirmed_Bug.
- **Counterexample**: The concrete input and observed output that demonstrates a failing Correctness_Property.
- **Confirmed_Bug**: A Correctness_Property whose Actual_Result is FAIL, reported with its Counterexample.
- **Lantern_Report**: The structured output that lists Correctness_Properties with their Predicted_Result, Actual_Result, any Counterexample, and any Property_Transition.
- **Property_Execution_Request**: The request sent to the MCP_Server containing the Correctness_Properties and the Target_Repo reference to execute.
- **Property_Execution_Result**: The structured response from the MCP_Server containing Actual_Results and Counterexamples.
- **Dependency_Install_Phase**: The execution phase that installs the Target_Repo dependencies, during which network access is permitted only to the package registry and install or lifecycle scripts are disabled.
- **Test_Execution_Phase**: The execution phase that runs the Correctness_Properties, during which all inbound and outbound network access is disabled.
- **jsdom**: A JavaScript implementation of web standards that provides a headless DOM environment in which a React component can be rendered without a browser.
- **Controllable_Clock**: A test-provided clock that fixes and controls the current time so that time-dependent behavior is deterministic during execution.
- **Execution_Context**: The recorded set of reproduction values for a single execution, comprising the Random_Seed, the timezone, and the Fixed_Current_Time, sufficient to replay the execution and reproduce the same Actual_Result.
- **Random_Seed**: The seed value used to initialize random generation for an execution, recorded as part of the Execution_Context.
- **Fixed_Current_Time**: The fixed value of the current time supplied by the Controllable_Clock for an execution, recorded as part of the Execution_Context.

## Requirements

### Requirement 1: Reverse-Engineer a Kiro Spec from a Target Repo

**User Story:** As a developer reviving an abandoned app, I want spec-lantern to reverse-engineer a Kiro spec from my Target_Repo, so that I have an explicit statement of what the app is supposed to do.

#### Acceptance Criteria

1. WHEN a Target_Repo is provided and contains at least one analyzable TypeScript source file, THE Kiro_Power SHALL generate a requirements document in which each distinct Target_Repo behavior it identifies is expressed as at least one criterion that conforms to one of the six EARS patterns.
2. WHEN a Target_Repo is provided and contains at least one analyzable TypeScript source file, THE Kiro_Power SHALL generate a design document that includes a non-empty Correctness_Properties section containing at least one correctness property for each generated requirement.
3. WHERE a Target_Repo contains code comments describing intended behavior, THE Kiro_Power SHALL record each such described behavior as a distinct Claim in the generated spec, with each Claim referencing the source file and comment it was derived from.
4. IF a Target_Repo cannot be read (for example, the path is inaccessible or no file can be opened), THEN THE Kiro_Power SHALL report that reverse-engineering cannot proceed, SHALL include a human-readable message identifying the specific reason, and SHALL NOT produce a partial or incomplete spec.
5. IF a Target_Repo is readable but contains no analyzable TypeScript source file (that is, zero files with a recognized TypeScript extension that parse without fatal syntax errors), THEN THE Kiro_Power SHALL report that reverse-engineering cannot proceed and SHALL include a message indicating that no analyzable TypeScript source was found.

### Requirement 2: Separate Intended Behavior from Current Behavior

**User Story:** As a developer, I want spec-lantern to distinguish what the app claims to do from what it actually does, so that I can see where the app diverges from its documented intent.

#### Acceptance Criteria

1. WHEN analysis of the Target_Repo completes, THE Kiro_Power SHALL produce an Observed_Deviations list where each entry enumerates one difference between a claimed behavior and the corresponding current behavior, and each entry contains a description of the claimed behavior, a description of the current behavior, and a reference to the originating Claim.
2. WHEN a Claim conflicts with current Target_Repo behavior, THE Kiro_Power SHALL record the conflict as an Observed_Deviation that includes a reference identifying the originating Claim.
3. WHERE no difference between claimed behavior and current behavior is found across all evaluated Claims, THE Kiro_Power SHALL produce an Observed_Deviations list containing zero entries.
4. IF a Claim cannot be evaluated against current Target_Repo behavior because the relevant behavior is absent or inaccessible, THEN THE Kiro_Power SHALL record an Observed_Deviation that references the originating Claim and indicates that the current behavior could not be determined, while retaining all other evaluated Claims in the Observed_Deviations list.

### Requirement 3: Extract Claims into Executable Properties

**User Story:** As a developer, I want every claim in code comments and requirements turned into a property, so that each stated behavior can be verified by execution rather than trusted by reading.

#### Acceptance Criteria

1. WHEN Claims have been identified in a Target_Repo, THE Kiro_Power SHALL convert each identified Claim into exactly one Correctness_Property.
2. THE Kiro_Power SHALL express each Correctness_Property as an executable test that terminates with a result of exactly one of PASS or FAIL.
3. IF a Correctness_Property test does not terminate within 60 seconds, THEN THE Kiro_Power SHALL halt that test and record its result as FAIL with a reason indicating the timeout.
4. WHEN Kiro converts a Claim into a Correctness_Property, THE Kiro_Power SHALL record a Predicted_Result of exactly one of PASS or FAIL for that Correctness_Property before that Correctness_Property is executed.
5. WHILE execution of a Correctness_Property has begun, THE Kiro_Power SHALL treat the recorded Predicted_Result for that Correctness_Property as immutable and SHALL use the originally recorded Predicted_Result value in any later comparison.
6. IF a Claim cannot be expressed as an executable Correctness_Property, THEN THE Kiro_Power SHALL record the Claim as unverifiable and SHALL record a reason indicating why the Claim could not be expressed as an executable Correctness_Property.

### Requirement 4: Test Logic Embedded in React Components

**User Story:** As a developer, I want spec-lantern to verify logic that lives inside React components rather than in exported functions, so that behavior defined only in component rendering is still checked by execution.

#### Acceptance Criteria

1. WHEN the Kiro_Power identifies logic that resides inside a React component and is not exported as a standalone function, THE Kiro_Power SHALL mark that logic as embedded component logic to be exercised through component rendering.
2. WHERE a Correctness_Property targets embedded component logic, THE MCP_Server SHALL render the React component in a jsdom environment with injected mocked data supplied to that component.
3. WHILE rendering a React component to evaluate embedded component logic, THE MCP_Server SHALL supply a Controllable_Clock so that time-dependent behavior produces a deterministic result.
4. WHEN a React component has been rendered in the jsdom environment, THE Kiro_Power SHALL derive a Component_Rendered_Property that asserts on the rendered output of that component.

### Requirement 5: Execute Properties in an Isolated Runner

**User Story:** As a developer, I want the properties executed against the real code in a sandbox, so that results reflect actual behavior and my host machine stays safe.

#### Acceptance Criteria

1. WHEN the MCP_Server receives a Property_Execution_Request, THE MCP_Server SHALL execute the included Correctness_Properties against the Target_Repo inside the Isolated_Runner.
2. THE MCP_Server SHALL execute Target_Repo code only inside the Isolated_Runner.
3. WHERE the Isolated_Runner is the local runner, THE MCP_Server SHALL run it as a rootless Podman container.
4. WHEN the MCP_Server executes a Property_Execution_Request, THE MCP_Server SHALL complete the Dependency_Install_Phase before the Test_Execution_Phase begins.
5. WHEN execution of a Correctness_Property completes without timeout or execution error, THE MCP_Server SHALL return an Actual_Result of exactly one of PASS or FAIL for that Correctness_Property.
6. WHEN a Correctness_Property produces an Actual_Result of FAIL, THE MCP_Server SHALL include in the Property_Execution_Result a Counterexample for that Correctness_Property that contains the input values that triggered the failure and the observed output.
7. IF execution of a Correctness_Property exceeds its allotted time limit of 30 seconds, THEN THE MCP_Server SHALL terminate that execution and SHALL return a timeout outcome for that Correctness_Property without returning a PASS or FAIL Actual_Result for it.
8. IF the Isolated_Runner cannot be created, THEN THE MCP_Server SHALL return an execution error that identifies the reason for the failure, and SHALL NOT execute any Target_Repo code on the host.
9. IF a Correctness_Property cannot be executed because the Target_Repo code raises an uncaught error or fails to load, THEN THE MCP_Server SHALL return an execution error for that Correctness_Property that identifies the reason, without returning a PASS or FAIL Actual_Result for it.

### Requirement 6: Record Reproducibility Context for Each Execution

**User Story:** As a developer, I want each execution to record the conditions that produced its result, so that any counterexample can be replayed exactly to reproduce the same outcome.

#### Acceptance Criteria

1. WHEN the MCP_Server executes a Correctness_Property, THE MCP_Server SHALL record an Execution_Context for that execution that contains the Random_Seed, the timezone, and the Fixed_Current_Time used during that execution.
2. WHEN the MCP_Server returns a Counterexample for a Correctness_Property, THE MCP_Server SHALL include the Execution_Context for that execution together with that Counterexample.
3. WHEN a Counterexample is replayed using the Execution_Context recorded with that Counterexample, THE MCP_Server SHALL produce the same Actual_Result that was recorded for the original execution.

### Requirement 7: Compare Predicted Results with Actual Results

**User Story:** As a developer, I want to see where the agent's read-only prediction disagreed with real execution, so that I can trust confirmed findings over misleading comments.

#### Acceptance Criteria

1. WHEN a Correctness_Property has both a recorded Predicted_Result and an Actual_Result of PASS or FAIL, THE spec-lantern SHALL pair the recorded Predicted_Result with the Actual_Result for that Correctness_Property.
2. IF a paired Predicted_Result and Actual_Result hold unequal PASS or FAIL values, THEN THE spec-lantern SHALL flag that Correctness_Property as a prediction mismatch.
3. WHEN a Correctness_Property has an Actual_Result of FAIL, THE spec-lantern SHALL classify that Correctness_Property as a Confirmed_Bug and SHALL associate the Counterexample returned for that Correctness_Property with the Confirmed_Bug.
4. IF a Correctness_Property has a timeout outcome instead of an Actual_Result of PASS or FAIL, THEN THE spec-lantern SHALL exclude that Correctness_Property from prediction-mismatch flagging and from Confirmed_Bug classification and SHALL mark it as not compared with an indication of the timeout outcome.
5. IF a Correctness_Property has a recorded Predicted_Result but no Actual_Result, THEN THE spec-lantern SHALL mark that Correctness_Property as not executed and SHALL not pair it as a prediction mismatch or classify it as a Confirmed_Bug.

### Requirement 8: Revive the Target Repo by Fixing Confirmed Bugs

**User Story:** As a developer, I want spec-lantern to generate and apply fixes for confirmed bugs on a copy of my app and re-check them, so that I can see which bugs are actually resolved without risking my original code.

#### Acceptance Criteria

1. WHEN a Correctness_Property is classified as a Confirmed_Bug, THE Kiro_Power SHALL generate at least one Fix_Task for that Confirmed_Bug.
2. WHEN a Fix_Task is applied, THE Kiro_Power SHALL apply the Fix_Task only to the Target_Repo_Copy and SHALL leave the original Target_Repo unmodified.
3. WHEN fixes for the Confirmed_Bugs have been applied to the Target_Repo_Copy, THE MCP_Server SHALL re-execute the same Correctness_Properties against the Target_Repo_Copy inside the Isolated_Runner.
4. WHEN a Correctness_Property is re-executed after a fix is applied, THE spec-lantern SHALL record both the Pre_Fix_Result and the Post_Fix_Result as the Actual_Result of that Correctness_Property before and after the fix.
5. WHEN both a Pre_Fix_Result and a Post_Fix_Result are recorded for a Correctness_Property, THE spec-lantern SHALL represent the Property_Transition from the Pre_Fix_Result to the Post_Fix_Result for that Correctness_Property.
6. IF a Correctness_Property has a Pre_Fix_Result of FAIL and a Post_Fix_Result of FAIL, THEN THE spec-lantern SHALL record a Property_Transition indicating that the fix did not resolve the Confirmed_Bug.
7. IF a Correctness_Property has a Pre_Fix_Result of PASS and a Post_Fix_Result of FAIL, THEN THE spec-lantern SHALL record a Property_Transition indicating that the fix introduced a regression in that Correctness_Property.

### Requirement 9: Produce the Lantern Report

**User Story:** As a developer, I want a Lantern Report that lists confirmed bugs with counterexamples and shows how fixes changed each property, so that I know exactly what to fix and what the fixes achieved.

#### Acceptance Criteria

1. WHEN comparison of Predicted_Results and Actual_Results completes, THE spec-lantern SHALL produce a Lantern_Report within 10 seconds of comparison completion.
2. THE Lantern_Report SHALL list each Correctness_Property with its Predicted_Result and its Actual_Result, including an entry for every Correctness_Property evaluated during the comparison.
3. WHERE a Correctness_Property is classified as a Confirmed_Bug, THE Lantern_Report SHALL include the Counterexample for that Correctness_Property, where the Counterexample identifies the input or state that triggers the deviation and the resulting Actual_Result.
4. THE Lantern_Report SHALL list each Observed_Deviation produced during analysis, where each listed Observed_Deviation includes the associated Correctness_Property and a description of how the Actual_Result differs from the Predicted_Result.
5. WHERE a Property_Transition is recorded for a Correctness_Property, THE Lantern_Report SHALL present the Pre_Fix_Result and the Post_Fix_Result for that Correctness_Property.
6. IF no Correctness_Property is classified as a Confirmed_Bug, THEN THE spec-lantern SHALL produce a Lantern_Report containing an indication that no Confirmed_Bug was found.
7. IF the comparison produces no Observed_Deviation, THEN THE Lantern_Report SHALL contain an indication that no Observed_Deviation was recorded.

### Requirement 10: Display Predicted versus Actual Results in the Web UI

**User Story:** As a developer, I want a web UI that shows predicted versus actual results per property, so that I can review findings visually.

#### Acceptance Criteria

1. WHEN a Lantern_Report is available, THE Lantern_Report_UI SHALL display each Correctness_Property with its Predicted_Result and its Actual_Result positioned adjacently within the same row.
2. WHEN a Lantern_Report is available, THE Lantern_Report_UI SHALL render all Correctness_Property entries contained in the Lantern_Report within 3 seconds of the Lantern_Report becoming available.
3. WHERE a Correctness_Property has a Predicted_Result that differs from its Actual_Result, THE Lantern_Report_UI SHALL apply a visual indicator to that Correctness_Property that is absent from Correctness_Property entries whose Predicted_Result equals its Actual_Result.
4. WHERE a Correctness_Property is a Confirmed_Bug, THE Lantern_Report_UI SHALL display the Counterexample for that Correctness_Property.
5. WHERE a Property_Transition is recorded for a Correctness_Property, THE Lantern_Report_UI SHALL display the Pre_Fix_Result and the Post_Fix_Result for that Correctness_Property.
6. IF a Correctness_Property is a Confirmed_Bug and no Counterexample is available for that Correctness_Property, THEN THE Lantern_Report_UI SHALL display an indication that the Counterexample is unavailable.
7. IF no Lantern_Report is available, THEN THE Lantern_Report_UI SHALL display a message indicating that no report exists.

### Requirement 11: Provide a Hosted Demo

**User Story:** As a reviewer, I want a publicly accessible hosted demo of the Lantern Report UI, so that I can view sample results without installing anything.

#### Acceptance Criteria

1. WHEN the Hosted_Demo is deployed, THE Hosted_Demo SHALL be reachable over the public internet without any local installation by the reviewer.
2. WHEN a reviewer opens the Hosted_Demo, THE Hosted_Demo SHALL present sample Lantern_Reports.
3. WHEN the Hosted_Demo presents a sample Lantern_Report, THE Hosted_Demo SHALL expose the predicted-versus-actual view, the Counterexample view, and the Property_Transition view that the local Lantern_Report_UI exposes.

### Requirement 12: Protect the Host Machine During Execution

**User Story:** As a developer, I want spec-lantern to never run untrusted target code on my host and to control network access per execution phase, so that analysis is safe.

#### Acceptance Criteria

1. THE spec-lantern SHALL execute Target_Repo code only inside the Isolated_Runner, with no Target_Repo process, script, or build step running in the host process or host shell.
2. WHILE the Dependency_Install_Phase is running inside the local Isolated_Runner, THE spec-lantern SHALL permit outbound network access only to the package registry and SHALL keep install and lifecycle scripts disabled.
3. WHILE the Test_Execution_Phase is running inside the local Isolated_Runner, THE spec-lantern SHALL keep all inbound and outbound network access disabled for the entire duration of that phase, from phase start until process termination.
4. IF a request would cause Target_Repo code to execute outside the Isolated_Runner, THEN THE spec-lantern SHALL reject the request before any Target_Repo code runs, SHALL report a safety violation indicating the request was blocked, and SHALL leave the host filesystem and host process state unchanged.
5. IF the Isolated_Runner cannot be started or is unavailable, THEN THE spec-lantern SHALL abort Target_Repo execution, SHALL report an error indicating the runner is unavailable, and SHALL NOT fall back to executing Target_Repo code on the host.
6. WHILE Target_Repo execution is running inside the Isolated_Runner, THE spec-lantern SHALL restrict Target_Repo file access to the Isolated_Runner boundary and SHALL prevent reads or writes outside that boundary.
